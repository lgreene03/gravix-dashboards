# Charter review: 2026

**Period:** 2026-01-01 to 2026-09-16
**Published:** 2026-09-16
**Anniversary:** the charter was ratified during Horizon 2; this first review is published at the
end of the roadmap that created it rather than waiting a further year for an anniversary that has
not arrived.

This is the first review. It covers Horizon 2 to date, and it is short on measured numbers for
reasons section 3 is mostly about.

---

| No core package imports `ee/` | `make check-boundary` | 0 violations |

## Where we fell short

Six items, and the first is the one that matters most.

- **External contributor share: no number, and the real figure is almost certainly 0%.** The target
  is ≥30% by the exit of Phase 12, which has passed. This repository has had no non-founder
  contributors, so the ladder in `docs/oss/contribution-ladder.md` has never been climbed, and
  GRVX-1210 is recorded `partial` for exactly this reason (SD-037). The machinery for onboarding a
  maintainer is built and tested; nobody has used it. **This is a miss, not an unmeasurable.**

- **Time to first correct dashboard: not aggregated.** The `timed-onboarding` CI job measures it per
  run and nothing collects a median. The target is ≤10 minutes and we do not know whether we meet
  it, which is a gap in evidence rather than in the product.

- **OSS build green percentage: not queried.** `make build-oss` and `make test-oss` run on every
  pull request and have passed on every commit in this roadmap, but this tool does not read Actions
  history, so the review cannot state a percentage. "Green every time I looked" is not a
  measurement.

- **OSS 30-day retention: permanently unmeasurable.** Gravix collects no telemetry (charter §7.4),
  so there is no retention number and there never will be one from this side. G7.4's canary depends
  on it, which means **the canary cannot currently trip** — it is a tripwire with one end
  unattached. This is the most uncomfortable finding in the review and it is a direct, accepted
  consequence of the no-telemetry promise. A proxy would be a dark pattern in a document about not
  having dark patterns.

- **Pro monthly recurring revenue: zero, because there is no Pro.** The `ee/` tier is built and
  source-available; nothing is sold. The canary's other end is unattached too.

- **Nine specs sat marked `done` in a register nothing checked**, until F-044. Three roadmap
  sources disagreed with reality and nobody would have known. The audit that catches it now exists
  because it was found by accident, which is its own finding about how many other claims were
  unchecked.

## Charter violations

None found. The commands that checked:

| Check | Command | Result |
|---|---|---|
| Capabilities moved into `ee/` | `make charter-evidence` → `capabilities_moved_to_ee` | `[]` — but see below |
| Core imports `ee/` | `make check-boundary` | `boundary: 0 violations` |
| Core builds with `ee/` deleted | `make build-oss && make test-oss` | both exit 0 |
| Upsell in the free dashboard | `make charter-evidence` → `upsell_elements_found` | `0` |
| Artificial limits | `make charter-evidence` → `artificial_limits_found` | `0` |
| A CLA has appeared | `make charter-evidence` → `cla_exists` | `false` |

**One caveat on the first row, stated rather than buried.** `capabilities_moved_to_ee` is `[]`
because there is no commit before 2026-01-01 to diff `boundary.yaml` against — the repository's
history does not reach back that far. So the empty list means "nothing to compare", not "compared
and found nothing". The check works and is tested; it simply had no prior state to read. Next
year's review will have one.

Every `ee/` capability records all five Crippleware Test answers: `100%`, and `pkg/boundary`'s own
validation would fail the build otherwise.

## The canary

G7.4: OSS 30-day retention against Pro monthly recurring revenue.

| | Trend |
|---|---|
| OSS 30-day retention | **unknown** — no telemetry exists to measure it (§7.4) |
| Pro MRR | **unknown** — nothing is sold |
| Tripped | no |

`unknown` means it was not checked, not that it is fine.

The honest reading: **the canary is not currently capable of tripping.** Both inputs are unknown and
one of them is unknowable by design. That is not a failure of the implementation — it computes the
conjunction correctly and a test proves it — it is a gap between what G7.4 asks for and what the
no-telemetry promise permits.

When Pro is sold, MRR becomes knowable. Retention will not be. Whatever replaces it has to come from
consenting, opt-in signal, and if nothing acceptable exists then G7.4 needs rewriting rather than
quietly satisfying with a proxy.

## What we are changing

Nothing this year.

The charter's prose has not been amended, and no §6 RFC has been opened against it. The one
structural change is **§6.1 itself**, added by GRVX-1501's sibling GRVX-1508 to make this review a
procedure rather than an intention — an addition, changing no existing section and no entrenched
clause.

**Entrenched clauses are excluded** from anything this review could propose. §7.1, §7.3 Q4 and §7.4
may be strengthened and never weakened, and `charterreview.CheckAmendment` refuses a proposal that
would before it is published.

## What we are not changing, and why

- **The ≥30% external contributor target stays**, despite being missed by the whole of it. Lowering
  a target because it was not met is how a goal tree becomes a description of what already happened.
  The number is a statement about what a trustworthy open-core project looks like, not a forecast.

- **No CLA, permanently.** Nobody asked for one this year. It is recorded here anyway, because the
  year somebody does ask is the year this line matters, and a decision made in advance is harder to
  reverse quietly than one made under pressure.

- **No telemetry, even to fix the canary.** The cleanest way to make G7.4 work would be to measure
  retention, and measuring retention means collecting data from installations we do not own.
  Section 5 is the cost of refusing, and it is the right cost to pay: a promise that survives only
  while it is convenient was not a promise.

- **`ee/` keeps every capability it has.** Nothing moved in and nothing needs to move out. The four
  Phase 13 and Phase 14 features placed there — fleet, intelligence, warehouse sync,
  bring-your-own-bucket, the spend cap, the SLA engine — each answer all five Crippleware Test
  questions `no`, and the free product runs unchanged with `ee/` physically deleted on every pull
  request.
