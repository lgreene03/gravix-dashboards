## 1. Objective

Publish what Gravix is working on, what it is not, and why — generated from the goal tree and the
spec index rather than maintained by hand, so it cannot quietly go stale. Let the community signal
priority without that signal becoming an obligation.

## 2. Context the implementer needs

- `docs/oss/12-goal-tree.md` holds G1–G9 with KRs and their measurement sources; Loop L1 refreshes it monthly.
- `docs/oss/specs/SPEC-INDEX.md` is generated by `scripts/gen_spec_index.py` from spec headers.
- `docs/oss/20-roadmap-horizon-2.md` holds phases, deliverables and exit criteria.
- `docs/04-non-goals.md` lists seven permanently-rejected categories.
- `docs/oss/11-agent-loops.md` §L1 is the monthly reprioritisation loop this board reports.
- `docs/oss/12-goal-tree.md` §Goals deliberately NOT set records rejected goals so they are not re-proposed each quarter — the board should surface that too.

## 3. Non-goals for this spec

- Do NOT hand-maintain the board. A hand-written roadmap page is stale within two months and then actively misleading.
- Do NOT let voting decide anything. Votes are a signal for L1, not a mandate; a popularity-driven roadmap ends up building whatever the loudest cohort wants.
- Do NOT allow a vote to override a non-goal. `GOVERNANCE.md` already states this: *"Popularity does not amend the constitution."*
- Do NOT publish dates. Phase durations are estimates and publishing them as commitments invites exactly one kind of feedback.

## 5. Interface contract

### 5.1 Board sections, in order

1. `## What we are working on now` — the current phase, its goal, its specs and their status, from the spec index.
2. `## What is next` — the following phase's deliverables. No dates.
3. `## What we are deliberately not building` — the seven non-goals, each with the sentence explaining why, and a link to the tool that does do it. Placing this **third**, above the wishlist, is deliberate: most roadmap questions are really this question.
4. `## Goals we considered and rejected` — from the goal tree's "Goals deliberately NOT set" table, with reasons.
5. `## What the community has asked for` — open `roadmap-input` issues ranked by reaction count, each labelled with its disposition: `under consideration`, `accepted as SPEC <id>`, `declined — non-goal §<n>`, or `declined — <reason>`.
6. `## How this page is made` — states it is generated from the goal tree and spec index on every commit, names the script, and says a stale board is a CI failure rather than an oversight.

### 5.2 Disposition rules

Every community input reaches exactly one disposition, and nothing sits unlabelled:

| Disposition | When | Who |
|---|---|---|
| `under consideration` | Default on arrival; reviewed at the next L1 tick | `oss-steward` |
| `accepted as SPEC <id>` | L1 prioritised it and a spec exists | `cpo` |
| `declined — non-goal §<n>` | It falls in a permanently rejected category | `cpo` |
| `declined — <reason>` | Considered and rejected, with the reason stated | `cpo` |

An item may sit `under consideration` for at most **two** L1 ticks. After that it is accepted or
declined with a reason. Indefinite consideration is a decline that nobody has to defend.

### 5.3 What voting does

`docs/oss/roadmap-input.md` states verbatim:

```
Reactions on a roadmap issue tell us what people want. They do not decide what
gets built.

We read them at the monthly goal review, alongside our own incident data, the
adoption funnel, and what the charter allows. A heavily-supported request that
crosses a non-goal is still declined, and we will say so in that issue rather
than leaving it open to rot.

What voting genuinely changes: the order of things we were already going to
build, and our sense of which problem is most painful. That is a real influence,
and it is the honest description of it.
```

### 5.4 Generation and staleness

`scripts/gen_roadmap_board.py` reads the goal tree, the spec index and the roadmap, and writes
`docs-site/docs/roadmap.md` with a `<!-- GENERATED -->` first line. `make roadmap-check` fails if
the committed board differs from a fresh generation — the same pattern as GRVX-803 and GRVX-1204.

## 6. Behaviour

1. Implement the generator reading only from the three source documents plus the issue tracker.
2. Generate the board with all six §5.1 sections in order.
3. Write `roadmap-input.md` with the §5.3 statement verbatim.
4. Write the input issue template asking for the **problem**, not the proposed feature — the same discipline as the feature-request template from GRVX-705.
5. Add the Makefile targets and the CI staleness check.
6. Verify no date appears anywhere on the board.
7. Verify every non-goal on the board names an alternative tool.

### 6.1 Failure modes

| Trigger | Behaviour | Exact message |
|---|---|---|
| Board stale | CI fails | the `diff -u` output |
| An input item `under consideration` past two ticks | generator warns, exit 1 | `roadmap: input #<id> has been under consideration for <n> ticks; decide it` |
| A date appears in generated output | generator fails | `roadmap: generated board contains a date; phase durations are estimates, not commitments` |
| A non-goal without an alternative tool | generator fails | `roadmap: non-goal §<n> names no alternative tool` |

## 10. Escalation

| If you find… | Do this |
|---|---|
| Pressure to publish delivery dates | Refuse, citing §3. Estimates published as commitments generate one kind of feedback and no useful planning. |
| A heavily-supported request that crosses a non-goal | Decline it in the issue, citing the section, naming the tool that does it. Do not leave it open. |
| An item stuck under consideration | Force the decision at the next L1 tick. Indefinite consideration is a decline nobody has to defend. |
